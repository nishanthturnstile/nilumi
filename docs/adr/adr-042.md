# ADR-042 — Tool broker, fail-closed policy and immutable approvals

> **Status:** Accepted
> **Baseline:** October 8, 2026
> **Origin:** Owner-approved plan from the October 8 reference-architecture review, revised after an independent final review
> **Legacy references:** None
> **Supersedes / superseded by:** None. Builds on [ADR-007](adr-007.md), [ADR-010](adr-010.md), [ADR-018](adr-018.md) and [ADR-041](adr-041.md)

## Context

Agent runs and suggestions in the Today brief can propose actions. A model
proposal must not become an authorization. The
[reference repositories](../research/04-research.md#reference-repositories-claims-checked-8-oct-2026)
show useful patterns:
- OpenBot's policy separates the mechanism from the effect and the acting person from the run initiator, and it fails closed.
- OpenDots approvals store the exact connection, tool and arguments, run the stored request and recheck availability.
- OpenDots also shows a pattern to avoid: new tools are enabled by default, and MCP `readOnlyHint` sets the initial approval.

[MCP 2026-07-28](../research/04-research.md#platform-constraints) says clients must
treat tool annotations as untrusted.

## Decision

**Broker.** Every tool call from a bounded agent run, and every action proposed
for approval, passes through one server-side broker. It runs these stages:
1. Resolve the tool.
2. Evaluate policy.
3. Record the decision.
4. Execute.
5. Record a receipt.

Constrained commands keep their existing executor path and receipts.

**Registry.** Each tool declares:
- its mechanism: name, version and input schema
- an effect class: read, reversible internal write, irreversible internal write, notification, external read or external write
- the data scopes it touches

Declaring a tool does not grant it.

**Policy.**
- Inputs separate the *actor*, whose authority and RLS visibility are used, from the *initiator*: a member, a routine, a schedule or an agent run.
- Policy fails closed: any unmatched request is denied. The default policy is an explicit, versioned object in code:
  - Reads are limited to the actor's RLS visibility.
  - Reversible internal writes from constrained commands keep undo-first behaviour ([ADR-010](adr-010.md)).
  - Internal writes proposed by agent runs or brief suggestions require approval.
  - Notifications follow existing reminder and push rules.
  - External writes are denied until a later ADR.
- MCP tool annotations and other server-supplied hints are untrusted and never relax policy. Any future MCP tool starts disabled.

**Approvals.**
- **Binding.** A proposal stores immutable arguments bound to the actor, household, connection (if any), tool name and version, target-record revision, policy version and expiry.
- **Edits and decisions.** Editing creates a new proposal and supersedes the old one. Approve, reject and expire decisions are recorded.
- **Dispatch.** On approval, the server rechecks authorization, policy, tool availability and target revision. It runs only the stored arguments, never arguments sent with the approval. Consuming the approval and writing the invocation receipt happen in one transaction, so an approval cannot be replayed.
- **Who approves.** Only the actor can approve. A proposal cannot touch another member's private data.
- **Routine pushes.** Pushes the member has already authorized, such as reminders and their own brief, need no approval for each send.

Before the pilot, approval cards cover internal actions only.

## Alternatives

- **Trust model or tool annotations to decide when approval is needed.** Rejected as unsafe.
- **Approve by tool name only.** Rejected: arguments and targets could change after approval.
- **Ask for confirmation on every write.** Rejected: it contradicts undo-first behaviour for explicit commands.
- **Use AI SDK `toolApproval` statuses alone.** Not sufficient: the SDK only emits the approval request. Persistence, binding and rechecks remain Nilumi's responsibility.

## Consequences

Approvals become auditable records that cannot be replayed. The UI needs a
card to approve, edit or reject ([ADR-044](adr-044.md)). New tables (approvals
and tool_invocations) need RLS and forget scrubbing. A minimal `tool_invocations`
table ships with `approvals` before the pilot and holds each approval's receipt;
`mutation_receipts` stays the offline list, task and inbox ledger
([Architecture §6.6](../core/02-architecture.md#66-tool-broker-policy-and-approvals)). Red-team evals must cover
approval replay, argument substitution, stale targets and cross-member
proposals.
