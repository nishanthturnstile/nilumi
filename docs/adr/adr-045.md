# ADR-045 — Read-only Google Calendar for each adult in the Today brief

> **Status:** Accepted
> **Baseline:** October 8, 2026
> **Origin:** Owner decision during the October 8 planning review (read-only Google Calendar for both adults, per-person OAuth, no CalDAV), revised after an independent final review
> **Legacy references:** None
> **Supersedes / superseded by:** None

## Context

The Today brief is more useful when it includes each adult's calendar. Both
adults use Google Calendar. The [October 8 review](../research/04-research.md#platform-constraints)
found:
- Read scopes are sensitive rather than restricted. This is high confidence but not confirmed per scope from a primary source.
- In Testing mode, refresh tokens expire after seven days.
- A published but unverified app shows a warning screen and has a 100-user cap.
- `events.list` does not allow `syncToken` together with `timeMin`/`timeMax`.
- Better Auth supports `linkSocial` and `getAccessToken`, with refresh.

Sign-up is invite-only ([ADR-023](adr-023.md)), so linking must not open a
Google sign-up path.

## Decision

**Scope and linking.**
- Each adult links their own Google account through Better Auth `linkSocial` with offline access and `calendar.events.readonly` only.
- The server checks the granted scopes and reads the primary calendar only. There is no write scope.
- Linking never creates a Nilumi account.
- Linking must be tested from both installed PWAs.

**OAuth app state.** The app is published (unverified, fewer than 100 users),
because Testing mode's seven-day token expiry would break the brief.

**Tokens.**
- Tokens are encrypted at rest. Key handling is documented with the backup material ([ADR-032](adr-032.md)).
- Tokens are read only on the server, by account ID and owning user.
- Refreshes are serialized per account.

**Sync.**
- Bounded-window polling with `timeMin`/`timeMax` covers today and tomorrow in Asia/Kolkata, without sync tokens.
- A refresh runs before the brief is assembled.
- Recurring, all-day and time-zone handling follows [Architecture §13.5](../core/02-architecture.md#135-read-only-google-calendar-connection).
- When data is stale, the brief shows a stale marker. An expired or revoked token shows a Reconnect chip, and the brief still works without calendar items.

**Visibility.** Imported events are private to their owner by default, are
not memories and never leak their existence ([ADR-031](adr-031.md)). Calendar
text is untrusted data and never becomes instructions to a model.

**Disconnect.** Disconnecting revokes the token at Google, fences any sync in
progress, deletes the cached events and scrubs derived brief items.

**Gate.** Spike S-GCAL must pass before family use.

## Alternatives

- **CalDAV or ICS links.** Rejected: weaker authentication, and secret ICS URLs act as bearer credentials.
- **Calendar write access.** Deferred to a later horizon, which would need approval cards ([ADR-042](adr-042.md)) and a new ADR.
- **Push notification channels and sync tokens.** Deferred: the bounded window is simpler at household scale and avoids channel renewal.
- **One shared household Google account.** Rejected: it breaks per-member privacy.

## Consequences

Google becomes a data source, recorded as a provider in Tech Stack §7. The
OAuth warning screen is accepted for two known users. Token expiry and
revocation become visible states in the UI. The tables `connections` and
`calendar_events_cache` need RLS, forget handling and export decisions.
