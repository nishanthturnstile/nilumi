# ADR-012 — Railway (Singapore) hosting: Next.js app, worker and Postgres; Dokploy VM as exit path

> **Status:** Accepted
> **Baseline:** Revision 2, reviewed 6 Oct 2026; individual decision date not recorded
> **Origin:** Extracted from Architecture §21; existing ID and accepted meaning retained
> **Legacy references:** D5

## Context

The owner already has a paid Railway account and wants app, worker and database together near India.

The hosting comparison weighs lower marginal VM cost and serverless free tiers against owner operations and runtime fit. Always-on Railway supports graphile-worker and SSE, while unmanaged Postgres remains an explicit responsibility. Revision 1 briefly selected Vercel Hobby + Neon; revision 2 returned to Railway under the free-OSS-only Vercel rule.

## Decision

start on Railway Singapore with `app`, `worker` and Railway Postgres 18 + pgvector, using the owner's existing paid account.

## Alternatives

existing Dokploy VM first, Fly.io, Render, split app/database providers, managed Postgres only.

## Consequences

the first deployment is always-on, close to India and operationally simple; we must operate Postgres; the same Docker image and `docker-compose.yml` keep a Dokploy exit path.

S5 must prove resource cost, database extensions, streaming and recovery. Managed Postgres remains an exit option if database operations become a burden.
